# Building and verifying a release

Harmost is a proxy: it terminates your traffic and decides which responses may
be shared between users. Being able to rebuild a published artifact yourself,
and get the same bytes, is the difference between trusting the code and
trusting whoever ran the build.

## Building from source

```bash
git clone https://github.com/OWNER/harmost
cd harmost
cargo build --release --locked
```

The toolchain is pinned in [`rust-toolchain.toml`](../rust-toolchain.toml), so
`rustup` fetches the exact compiler CI and the release builds use. `--locked`
refuses to update `Cargo.lock`; without it a dependency published five minutes
ago silently enters your proxy.

### Features

```bash
cargo build --release --locked --features tls
```

`tls` compiles rustls termination (`server.tls`) and origin TLS
(`origin.tls`). It is off by default because most deployments terminate TLS at
a load balancer and an unused TLS stack is unused attack surface. A binary
built without it **rejects** a config containing those keys rather than quietly
serving cleartext, and `harmost version` prints which features are compiled in.

rustls rather than boringssl or openssl: it is pure Rust, so the build needs no
`cmake`, no Go and no system OpenSSL headers.

### Build requirements

- Rust as pinned in `rust-toolchain.toml`.
- A C toolchain and `cmake`, for the C dependencies Pingora pulls in.
- On Debian/Ubuntu: `clang cmake libssl-dev pkg-config`.

## Verifying a published release

Every release publishes, for each target:

- `harmost-<version>-<target>.tar.gz` — the binary, `LICENSE` and `README.md`
- `SHA256SUMS` — checksums for every archive in the release
- `harmost-<version>.cdx.json` — a CycloneDX SBOM of the source dependency tree

```bash
VERSION=0.1.1
TARGET=x86_64-unknown-linux-gnu
BASE="https://github.com/OWNER/harmost/releases/download/v$VERSION"

curl -fsSLO "$BASE/harmost-$VERSION-$TARGET.tar.gz"
curl -fsSLO "$BASE/SHA256SUMS"

# --ignore-missing so this checks the one archive you downloaded rather than
# failing on the targets you did not.
sha256sum --ignore-missing -c SHA256SUMS
```

The container image carries build provenance and an SBOM attached as
attestations, so the same question has a stronger answer there:

```bash
IMAGE=ghcr.io/OWNER/harmost:0.1.1
docker buildx imagetools inspect "$IMAGE"

# Requires the GitHub CLI and gh-attestation.
gh attestation verify "oci://$IMAGE" --repo OWNER/harmost
```

Pin by digest, not by tag, for anything that matters:

```bash
docker pull ghcr.io/OWNER/harmost@sha256:<digest>
```

## Reproducible builds

The release binaries are built to be byte-for-byte reproducible from a clean
checkout of the tag. Three things make that possible, and all three are kept in
the repository:

1. **A pinned toolchain.** `rust-toolchain.toml` names an exact stable release.
   A different `rustc` produces a different binary, and "whatever was latest
   that week" is not a build description.
2. **A committed lockfile**, used with `--locked`.
3. **Path remapping.** [`scripts/reproducible-build.sh`](../scripts/reproducible-build.sh)
   derives the current checkout and Cargo-cache paths and rewrites them to
   stable placeholders. Hard-coding CI's paths would leave a local clone
   unmapped and make the reproducibility instructions false.

To reproduce a release yourself:

```bash
VERSION=0.1.1
git clone https://github.com/OWNER/harmost && cd harmost
git checkout "v$VERSION"

# Same target triple, same features as the published artifact. The release
# workflow builds Linux artifacts with --features tls.
./scripts/reproducible-build.sh --features tls \
  --target x86_64-unknown-linux-gnu

sha256sum target/x86_64-unknown-linux-gnu/release/harmost
```

Compare that against the checksum of the binary inside the published archive
(not of the archive itself — see below):

```bash
tar xzf "harmost-$VERSION-$TARGET.tar.gz" -O \
  "harmost-$VERSION-$TARGET/harmost" | sha256sum
```

If the two differ, that is a finding worth an issue. Please include your
`rustc -vV`, your target triple, and the feature list you built with.

## What the SBOM covers

`harmost-<version>.cdx.json` is CycloneDX, generated by `cargo cyclonedx` from
the resolved `Cargo.lock`. It lists every crate that is *resolved* for the
build, with versions and licences.

Two limits worth stating plainly, because an SBOM read as more than it is
becomes a false assurance:

- **Resolved is not the same as linked.** The lockfile contains crates that
  belong to optional features or to other platforms and are never compiled into
  the artifact you have. The SBOM over-reports rather than under-reports, which
  is the safe direction, but it does mean a listed crate is not proof of
  attack surface.
- **It covers Rust dependencies.** The runtime image also contains Debian
  packages (`ca-certificates`, `libssl3`, and the base system). Those are
  covered by the image SBOM that `docker buildx` attaches as an attestation,
  which is a different artifact and the one to read for the container.

Known-vulnerability status is a separate question from composition. CI runs
`cargo audit` on every push and the release gate re-runs it against the tagged
tree; [`.cargo/audit.toml`](../.cargo/audit.toml) records every ignored
advisory with a reason and a way out.

## What is not reproducible, and why

Stated rather than left for you to discover:

- **The `.tar.gz` archives are not byte-reproducible**, because gzip records a
  modification time. Verify the *binary* inside the archive, which is. The
  published `SHA256SUMS` covers the archives, so it answers "did I download
  what was published" — a different question from "was this built from that
  source".
- **The container image digest is not reproducible.** Image layers carry
  timestamps and are built on a base image that is itself rebuilt. Verify the
  image through its provenance attestation, which says which workflow, commit
  and runner produced it, rather than by rebuilding it.
- **macOS binaries are built on GitHub's macOS runners** and are not verified
  as reproducible. The Linux targets are the ones this section makes a claim
  about.
